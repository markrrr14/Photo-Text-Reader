01Overview

What the system is for, and what it actually does.

Photo Text Reader converts words visible in photographs into editable digital text. Manually retyping text from photographed notes, printed documents, signs, or learning materials is slow and error-prone. The application lets a user add an image, recognize the text with optical character recognition, review or correct the result, and then copy or export the extracted text.

The documented system is delivered as a single browser application. Its interface, input handling, OCR orchestration, editing, translation, and document export all run in the browser. Recognition is performed with Tesseract.js; there is no application server, database, or user account system. Internet access is required to obtain the OCR engine and language data the first time, and for machine translation.

Documentation basis

This page combines the project paper Photo Text Reader with source inspection of the shipped application file, phototextreader.html. Where the paper and the shipped edition differ, both are reported in Paper vs. implementation rather than silently reconciled.

Evidence status

The supplied material contains source code but no verified screenshots or recorded execution logs. No screenshots are reproduced here, and test results remain pending until they are actually observed in Chrome. A mockup is not evidence that a feature worked.

04How it works

The operator's path through the application, from photo to finished text.

  1. Open the application and choose languagesThe OCR language describes the text in the photos. A translation target is optional. Both choices are remembered in browser storage.
  2. Add photos or filesUse the file picker, the camera capture input, or drag and drop. Images and PDFs can be mixed in one batch, up to 20 pages.
  3. Prepare the pagesImages are redrawn onto a canvas and re-encoded as JPEG bounded to 1800 pixels on the longest side. PDFs are rasterized at 2× scale, limited to the first 10 pages per file.
  4. Recognize textEach page is processed in order. The OCR path converts the image to grayscale, applies an automatic threshold, and trials up to three variants, keeping the best-scoring result. Progress and per-page state are shown.
  5. Review and editRecognized text appears in a per-page editable field, with a running word count. Lines that fail a minimum character test are discarded during cleanup.
  6. Translate if neededWhen a target language is selected, each non-empty page is translated in chunks and shown beneath its extracted text.
  7. Copy or exportCopy a single page, copy all pages, or download a .docx file containing every page and its translation.

Changing the OCR language marks all pages for re-reading. The read action doubles as a stop control while processing is running.

06Data flow

Where the data goes, and where it does not.

The selected image remains in the browser workflow. Flutter reads the file into bytes and converts it to a data URL for the JavaScript OCR function in the paper's build; in the shipped HTML edition, the file is read into a blob URL for preview and drawn to a canvas for recognition. Recognized text is returned to the interface and displayed for editing.

Copying uses the clipboard API with a fallback that selects the text. Downloading creates the document entirely in the browser and saves it locally. Language preferences are stored in localStorage. No database, account, or server-side storage is implemented, and the selected photo is not sent to an application server.

Stays local

Photos and results

Page images, object URLs, extracted text, edits, and generated documents remain in the browser session.

Network

Engine and translation

Tesseract.js and its language data are fetched from a CDN. Translation requests go to a remote service. PDF support is also loaded from a CDN.

08Technology stack

Libraries and browser capabilities the system depends on.

Recognition

Tesseract.js 5.1.1

Loaded from cdnjs. Workers are cached per language. When the page runs inside a hosted reader environment, that reader is used instead of local OCR.

PDF

pdf.js 3.11.174

Loaded from cdnjs with a matching worker. Renders each page to a canvas for recognition.

Image processing

Canvas 2D

Resizing, JPEG encoding, grayscale conversion, Otsu thresholding, and variant generation.

Translation

Remote translation endpoint

Source language is detected automatically. Text is split at 1200 characters and reassembled.

Export

Custom ZIP and OOXML writer

A small CRC-32 and ZIP store implementation assembles the DOCX package without any external archive library.

Platform

Modern web browser

No build step and no backend. Chrome is the target used in the paper's testing plan.

09Scope and limitations

Boundaries that affect what may be claimed about the system.

  • Web-only in practice. The paper's Flutter service stub explicitly reports OCR as unsupported on non-web platforms. Android and Windows OCR must not be assumed.
  • Network dependency. The OCR engine and language data are fetched from a CDN, PDF support is fetched from a CDN, and translation requires a remote service. There is no offline engine packaging.
  • Accuracy is conditional. Recognition quality depends on image sharpness, lighting, contrast, language selection, and page layout. Preprocessing improves the odds but cannot guarantee correctness.
  • Bounded batches. At most 20 pages per batch and 10 PDF pages per file. Images are downscaled to 1800 px, which can lose very small text.
  • No persistence layer. No database, accounts, or server storage. Refreshing the page discards the working set; only language preferences survive.
  • Third-party translation. The translation feature depends on an external endpoint that may change, rate-limit, or become unavailable.
  • Evidence gap. No completed runtime tests, screenshots, or measurement logs were supplied. Performance and accuracy claims require measurement.
Do not overclaim

The system can be described as implementing a browser OCR workflow. It cannot yet be described as proven faster or more accurate than manual retyping until Test 5 in the testing plan is actually carried out and recorded.

11Conclusion

What the source implements, and what should come next.

What the source implements

The project contains a browser-based workflow for adding photos and PDFs, performing Tesseract.js OCR with image preprocessing, displaying editable recognized text per page, showing processing progress and counts, translating results optionally, and copying or exporting text as a DOCX file. These are findings from source inspection, not proof of successful execution on a particular computer.

Limitations

OCR is explicitly unsupported on non-web platforms in the paper's service stub. Initial engine and language-data loading depends on network access. Batches and PDF page counts are bounded, image dimensions are capped, and poor-quality images may produce recognition errors. The project includes no documented completed functional tests and no server-side storage.

Recommendations

  • Test with a range of image qualities, scripts, and page layouts, and record recognition accuracy.
  • Measure OCR time against manual retyping on identical source material.
  • Improve user-facing error guidance for network failures, unreadable pages, and clipped PDFs.
  • Evaluate offline engine packaging so the reader works without a CDN.
  • Consider native-platform OCR only if support outside the browser is a real requirement.

12Paper vs. implementation

The reference document and the shipped HTML edition describe related but not identical systems.

The project paper documents a Flutter and Dart web application. The file supplied alongside it, phototextreader.html, is a standalone browser edition with additional input, translation, and export features.
